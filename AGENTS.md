[`README.md`](README.md) decides fit and gives the quickstart. [`docs/REFERENCE.md`](docs/REFERENCE.md)
is generated by `bun run docs` and is never hand-edited. There is no roadmap, plan directory, status ledger, or decision log here;
those change on another lifecycle and live outside the repository.

## Surface earns its place, and there are two ways to earn it

- [`recipes/personal-agent`](recipes/personal-agent/README.md) — the log, compaction, context
  lifetimes, tools, cross-session search.
- [`recipes/agent-service`](recipes/agent-service/README.md) — the queue, atomic cross-session
  handoff, a harness and a sandbox per session, live views.
- The conformance suites — what an adapter must prove, for the implementations that are not here.

**Surface with no consumer should not exist. A recipe that composes it is one consumer; a
conformance suite that holds an adapter to it is the other.** `exports-consumed` enforces both, for
every exported value, across every file a declared subpath resolves to — and a suite earns its place
by being *run* against an implementation here, not by being a suite, so an exported case list
nothing executes is still a violation. A type is public surface the moment a value's signature names
it, and an option on a call never appears in an import at all, so those two are judgment and the
gate is green either way.

This rule used to say the two recipes *were* the specification, and that anything they did not call
should not exist. That was written before the ports had implementations outside this repository, and
it had gone quietly false: a conformance suite is consumed by adapter authors, not by recipes, and a
port with three implementations is a promise about all three. Keeping the old wording would have
argued the suites out of existence.

What has not changed is the part that bites: a seam nobody exercises is a seam nobody is holding to
account, and it will be wrong. `price` and `limits.maxUsd` shipped with no consumer at all and were
caught by an audit rather than by the gate — the type checker cannot see an option that is never
passed, so this one stays judgment and stays yours.

## The judgment rules

`docs/CODE.md` carries the discipline in full. These three decide most reviews:

- **One name per fact.** A fact has exactly one word across the package, and no field holds a value
  another field already determines. A second word for an existing fact is a defect; so is a second
  field for an existing value.
- **No simulated guarantees.** Declare what you actually do. A capability you lack fails typed —
  nothing fabricates a transcript, resume state, isolation, or usage.
- **A failing check is a decision, not an obstacle.** Fix the code, or change the check deliberately
  in the same commit with the reason in the message. Challenging a check is a diff, not an argument.

## Before you change anything

1. Read the document that owns the claim you are about to change.
2. Inspect the code and the tests that exercise the behaviour.
3. Find the smallest owning layer, and the contracts it may depend on.
4. Ask whether the request exposes a problem in the contract rather than only the implementation.

Do not mechanically accept a premise, including one from this repository's own documentation. If
implementation evidence invalidates a documented decision, correct the document deliberately,
explain why, then implement the corrected design.

## The gate

`bun run check` is the green gate. Report failures; never hide them. `docs/CODE.md` says what it
covers and how to argue with it.
