# personal-agent

One operator, one machine, one SQLite file. This is the recipe that proves the
log, compaction, context lifetimes, tools, and session listing.

```bash
bun run recipe personal-agent "what did I decide about the pricing model?"
```

## What it demonstrates

| Concern | Where it lives |
| --- | --- |
| Conversation history, resume | aglib — the session log |
| Keeping a long conversation in budget | aglib — compaction in the native harness |
| Remembered facts | this recipe — a `facts` table and two tools |
| Skills | this recipe — markdown files and one tool |
| Cross-session search | this recipe — SQLite FTS5 over the log |
| Session list and titles | aglib `store.list` + app-written metadata |

Everything anyone calls "memory" is in the right-hand column except the first
two rows. The library provides the log and two context slots; the rest is
application code sitting in the same database.

## The indexing opinion

Three grains, and the decision that matters is what is left out:

- **Per session** — a title and short summary, generated by one model call when
  a run finishes, written to session metadata.
- **Per turn** — FTS5 over operator and assistant text, carrying `seq` so a hit
  reopens the log at the exact point.
- **Not tool results.** File dumps, command output and stack traces would swamp
  every query. Not embeddings either: FTS5 is already in SQLite, needs no
  service and no key, and `search_sessions` hides the implementation if that
  ever stops being enough.

## Context lifetimes

Facts and the skill index are **run-scoped** — they sit inside the cached
prefix and do not change mid-run. A fact written by `remember` applies from the
next conversation, because rewriting the cached prefix mid-run would invalidate
the cache on every subsequent turn. Search results arrive as ordinary tool
results and are never injected into the prefix.
